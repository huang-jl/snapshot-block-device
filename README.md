# 支持快照的块设备

在 Linux 64 位环境下，实现支持持久化快照的用户态虚拟块设备，无需内核驱动或挂载。
完成 `src/device.rs` 中的 `BlockDevice` 实现：

```rust
fn new(size: usize) -> Result<Self>;
fn read(&self, offset: usize, buf: &mut [u8]) -> Result<()>;
fn write(&mut self, offset: usize, buf: &[u8]) -> Result<()>;
fn snapshot(&mut self, dst: &Path) -> Result<()>;
fn open(layer: &Path) -> Result<Self>;
```

## 读写

- 设备大小固定，初始内容全为零，允许大小为零。
- 偏移和长度以字节为单位，支持任意对齐的读写。
- `read` 从 `offset` 开始读取 `buf.len()` 字节，成功时完整填充 `buf`。
- `write` 只覆盖指定范围，其余内容不变。
- 越界或范围计算溢出时返回错误；越界写入不得修改设备。
- 空读写允许偏移位于 `0..=size`，超过 `size` 仍然返回错误。
- 不同设备实例的写入互不影响。

## 快照

- `snapshot` 创建 `dst` 目录，在其中保存设备大小和内容，格式自行设计。
- 调用者保证父目录存在；若 `dst` 已存在，返回错误，不修改目标或设备内容。
- 快照成功后，当前设备可以继续读写，后续修改不影响已有快照。
- 创建快照的进程退出后，仍可通过 `open` 从快照目录恢复设备。
- 恢复后的设备可以继续读写和创建快照；从同一快照打开的多个实例互不影响，也不能修改原快照。
- 打开不存在的路径时返回错误。测试会保留所有快照目录及其路径。

第一阶段不限制实现方式和资源开销，不要求并发访问或掉电一致性。

cargo test --test snapshot

## 第二阶段

设备容量可能达到 **1 TiB**，单个设备累计写入的数据量不超过 **128 MiB**（重复覆盖写入也计入）。
保持接口和第一阶段的行为约定不变，
在 **256 MiB 的内存限制**下完成设备创建、读写、快照和恢复，不能因设备容量过大而 OOM。
允许利用本地文件系统存储设备数据，临时文件由实现自行管理。

可使用 `lib.rs` 提供的 helper 创建独立工作目录，避免多个设备使用同名文件时冲突：

```rust
let dir = crate::create_temp_dir()?;
let data_path = dir.path().join("data.bin");
```

快照应保存在 `dst` 中，不能依赖临时目录存活。

运行第二阶段测试：

```bash
cargo test --test large_device -- --test-threads=1
```

测试覆盖 1 TiB 设备的读写、累计 128 MiB 写入和快照恢复；测试本身使用小缓冲区。
当前命令不强制执行 256 MiB 内存限制。

## 第三阶段：增量快照

设备会反复创建快照，两次快照之间通常只有少量写入。
新快照应复用已有快照中未修改的数据，不能每次完整复制；接口及前两阶段的行为约定保持不变。

- 允许新快照依赖已有快照目录，测试会保留全部目录及其路径。
- 快照依赖的持久化数据必须保存在这些快照目录中，不能依赖临时文件或进程内存。
- 未修改的位置应保留历史内容；明确写入零的位置必须读出零。
- 从旧快照打开的设备同样需要支持增量快照，各分支互不影响。
- 本阶段不使用 reflink 或文件系统快照，快照内部格式自行设计。

验收场景：在 1 TiB 设备中写入 64 MiB 数据并创建首个快照，之后每轮不写入或仅写入 4 KiB。
每轮完成后，所有快照目录合计的实际磁盘占用最多增长 **2 MiB**（含索引和元数据）。
统计使用文件系统报告的已分配空间，硬链接按同一个文件计数，不按稀疏文件的逻辑长度计数。

```bash
cargo test --test incremental_snapshot -- --test-threads=1
```

## 第四阶段：限制内存中的数据量

设备逻辑容量仍为 **1 TiB**，累计写入量上限提高到 **1 GiB**。
本阶段将第二阶段的内存限制调整为：实现自行分配和管理的内存总量不得超过 **128 MiB**，
包括设备数据、数据副本、缓存、临时缓冲、索引及其他元数据。

设备创建、读写、快照和恢复过程中均需满足该限制。接口、读写语义和增量快照要求保持不变。
